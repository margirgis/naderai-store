# مستند المتطلبات

## 1. نظرة عامة على التطبيق

### 1.1 اسم التطبيق
نظام ربط المتجر مع Reseller API وإدارة طلبات شحن المحفظة مع تكامل GitHub - المرحلة الأولى

### 1.2 وصف التطبيق
نظام خلفي آمن يجمع بين:
- ربط المتجر مع Reseller API باستخدام بيئة Sandbox
- إدارة طلبات شحن محفظة Vodafone Cash مع نظام مطابقة تلقائية محسّن
- واجهة للعملاء لإنشاء طلبات الشحن
- واجهة للأدمن لإدارة الطلبات والموافقة عليها
- تطبيق Android لاستقبال رسائل SMS وإرسالها تلقائياً
- طبقة تكامل GitHub رسمية وآمنة لربط بيئة العمل بمستودع GitHub محدد

## 2. المستخدمون وسيناريوهات الاستخدام

### 2.1 المستخدمون المستهدفون
- العميل: يطلب شحن محفظته بالكريدت
- مدير النظام: يدير الاتصال مع Provider ويوافق على طلبات الشحن ويدير تكامل GitHub
- تطبيق Android: يستقبل رسائل Vodafone Cash ويرسلها للنظام

### 2.2 سيناريوهات الاستخدام الأساسية
- العميل يطلب شحن محفظته ويحوّل المبلغ المحسوب
- تطبيق Android يستقبل رسالة Vodafone Cash ويرسلها للنظام
- النظام يطابق الرسالة تلقائياً ويوافق على الطلب
- الأدمن يوافق يدوياً على الطلبات التي فشلت المطابقة
- الأدمن يختبر الاتصال مع Provider ويزامن الخدمات
- الأدمن يربط النظام بمستودع GitHub ويدير الملفات والتعديلات

## 4. القواعد والمنطق

### 4.1 الأمان

#### 4.1.1 حماية API Key
- API Key يجب أن يكون Server-side Secret/Environment Variable فقط
- عدم حفظ المفتاح في Database أو Source Code أو Logs
- عدم عرض API Key في Dashboard أو API responses

#### 4.1.2 معمارية الطلبات
- جميع طلبات Reseller API تمر من Backend
- Frontend لا يتصل مباشرة بـReseller API

#### 4.1.3 المصادقة والتفويض
- إضافة authentication وauthorization للـBackend endpoints
- إضافة basic rate limiting على endpoints الحساسة

#### 4.1.4 الاتصالات
- استخدام HTTPS للاتصالات
- منع تسريب secrets في error messages وlogs

### 4.2 إعدادات البيئة

#### 4.2.1 متغيرات البيئة
- PROVIDER_API_BASE_URL: https://api.geminioffer.web.id/api/v1
- PROVIDER_API_KEY: مفتاح Sandbox
- PROVIDER_ENVIRONMENT: sandbox
- GITHUB_TOKEN: Token المصادقة مع GitHub
- GITHUB_REPO_OWNER: اسم مالك المستودع
- GITHUB_REPO_NAME: اسم المستودع

#### 4.2.2 الاستخدام
- استخدام Sandbox فقط في هذه المرحلة
- النظام مجهز للانتقال إلى Live بتغيير Environment Variables فقط

### 4.3 Provider API

#### 4.3.1 المصادقة
- Authorization: Bearer ${PROVIDER_API_KEY}

#### 4.3.2 Response Envelope
- الهيكل: {success, data أو error, meta}
- فحص success وerror.code وdata

#### 4.3.3 Request ID
- حفظ request_id في logs

### 4.4 معالجة الأخطاء

#### 4.4.1 HTTP Status Codes
- 200: نجاح
- 400: طلب غير صحيح
- 401: مصادقة فاشلة
- 403: غير مصرح
- 404: غير موجود
- 429: تجاوز الحد
- 500: خطأ في الخادم
- 503: الخدمة غير متاحة

#### 4.4.2 عرض الأخطاء
- عرض رسائل خطأ واضحة
- عدم كشف secrets في رسائل الخطأ

### 4.7 نظام المطابقة التلقائية المحسّن

#### 4.7.1 معايير المطابقة
- رقم المرسل من SMS = sender_phone في الطلب
- |المبلغ من SMS - fingerprint_amount| ≤ 0.01

#### 4.7.2 أولوية المطابقة
- إذا تطابق أكثر من طلب: اختيار الأقدم

#### 4.7.3 حالات فشل المطابقة
- لا يوجد طلب معلق بنفس رقم المرسل
- المبلغ لا يطابق أي fingerprint_amount
- الطلب المطابق تمت الموافقة عليه مسبقاً

### 4.8 تحليل محتوى رسالة Vodafone Cash

#### 4.8.1 الأنماط المدعومة

- إنجليزي: You have received EGP [X] from [Name/Number] on [Date]. Transaction ID: [CODE]. Balance: [Y] EGP.

#### 4.8.2 البيانات المستخرجة
- sender_phone

### 4.9 الاستعداد للانتقال إلى Live

#### 4.9.1 متطلبات الانتقال
- تغيير PROVIDER_ENVIRONMENT من sandbox إلى live
- تغيير PROVIDER_API_KEY إلى مفتاح Live

### 4.10 GitHub Integration Security

#### 4.10.1 حماية Token
- GitHub Token يجب أن يكون Environment Variable فقط
- عدم حفظ Token في Database أو Source Code أو Logs
- عدم عرض Token في Dashboard أو API responses
- عدم إرسال Token إلى Frontend

#### 4.10.2 مبدأ أقل الصلاحيات
- طلب الصلاحيات الضرورية فقط:
  - repo (للقراءة والكتابة)
  - contents:write (لإنشاء وتحديث الملفات)
- عدم طلب صلاحيات إضافية غير مطلوبة

#### 4.10.3 التحقق من الصلاحيات
- التحقق من صلاحية القراءة قبل قراءة الملفات
- التحقق من صلاحية الكتابة قبل إنشاء أو تحديث الملفات
- رفض العملية إذا كانت الصلاحيات غير كافية

#### 4.10.4 معالجة الأخطاء
- عدم كشف Token في رسائل الخطأ
- عدم كشف معلومات حساسة عن المستودع
- تسجيل الأخطاء دون كشف secrets

### 4.11 GitHub API Usage

#### 4.11.1 المصادقة
- استخدام GitHub REST API v3
- إرسال Token في Header: Authorization: Bearer ${GITHUB_TOKEN}

#### 4.11.2 Rate Limiting
- احترام GitHub Rate Limits
- التعامل مع 403 Forbidden (rate limit exceeded)
- قراءة X-RateLimit-Remaining وX-RateLimit-Reset

#### 4.11.3 Endpoints المستخدمة
- GET /repos/{owner}/{repo}: جلب معلومات المستودع
- GET /repos/{owner}/{repo}/branches: جلب قائمة الفروع
- GET /repos/{owner}/{repo}/contents/{path}: قراءة محتوى ملف
- PUT /repos/{owner}/{repo}/contents/{path}: إنشاء أو تحديث ملف

### 4.12 GitHub File Operations

#### 4.12.1 قراءة ملف
- استدعاء GET /repos/{owner}/{repo}/contents/{path}?ref={branch}
- فك تشفير المحتوى من Base64
- حفظ SHA للاستخدام في التحديث

#### 4.12.2 إنشاء ملف
- تشفير المحتوى إلى Base64
- استدعاء PUT /repos/{owner}/{repo}/contents/{path}
- إرسال:
  - message: رسالة Commit
  - content: المحتوى المشفر
  - branch: اسم الفرع

#### 4.12.3 تحديث ملف
- جلب SHA الحالي للملف
- تشفير المحتوى الجديد إلى Base64
- استدعاء PUT /repos/{owner}/{repo}/contents/{path}
- إرسال:
  - message: رسالة Commit
  - content: المحتوى المشفر
  - sha: SHA الحالي
  - branch: اسم الفرع

### 4.13 GitHub Branch Management

#### 4.13.1 جلب الفروع
- استدعاء GET /repos/{owner}/{repo}/branches
- عرض اسم كل فرع
- عرض SHA آخر Commit

#### 4.13.2 الفرع الافتراضي
- جلب default_branch من معلومات المستودع
- استخدامه عند عدم تحديد فرع

### 4.14 GitHub Operations Logging

#### 4.14.1 العمليات المسجلة
- قراءة ملف
- إنشاء ملف
- تحديث ملف
- جلب قائمة الفروع
- التبديل بين الفروع

#### 4.14.2 البيانات المسجلة
- نوع العملية
- اسم الملف
- الفرع
- حالة العملية (نجاح / فشل)
- رسالة الخطأ (إن وُجدت)

- Admin المنفذ
- التاريخ والوقت

## 6. معايير القبول

1. العميل يفتح صفحة طلب الشحن ويرى رقم فودافون كاش الرسمي مع زر نسخ
2. العميل يدخل 2 كريدت ويرى السعر الإجمالي محسوباً تلقائياً مع زر نسخ المبلغ
3. العميل يدخل رقم محفظته ويضغط إرسال الطلب، ويُحفظ الطلب بحالة معلقة
4. العميل يحوّل المبلغ إلى رقم فودافون كاش الرسمي
5. تطبيق Android يستقبل رسالة Vodafone Cash ويرسل webhook للنظام
6. النظام يطابق الرسالة تلقائياً ويوافق على الطلب ويضيف الكريدت
7. الأدمن يفتح صفحة إدارة الطلبات ويرى الطلب بحالة موافق عليها
8. الأدمن يفلتر الطلبات حسب الحالة ويرى النتائج الصحيحة
9. الأدمن يفتح صفحة الإعدادات ويرى إحصائيات الشحن
10. الأدمن يفتح Provider Panel ويرى البيئة معروضة كـSANDBOX
11. Admin يضغط على Test Connection ويرى نتائج الاختبار
12. Admin يضغط على Sync Services وتظهر الخدمات المحدثة
13. Admin يضغط على Refresh Balance ويرى الرصيد محدثاً
14. Admin يفتح GitHub Integration Panel ويرى حالة الاتصال: غير متصل
15. Admin يدخل GitHub Token في Environment Variables ويضغط اختبار الاتصال، ويرى حالة الاتصال: متصل مع معلومات المستودع
16. Admin يختار ملف من قائمة الملفات ويضغط قراءة، ويرى محتوى الملف
17. Admin يدخل مسار ملف جديد ومحتواه ورسالة Commit ويضغط إنشاء، ويُنشأ الملف في المستودع
18. Admin يحدّث محتوى ملف موجود ويضغط تحديث، ويُحدّث الملف في المستودع مع Commit جديد
19. Admin يفتح إدارة الفروع ويرى قائمة الفروع المتاحة مع آخر Commit
20. Admin يفتح سجل العمليات ويرى جميع عمليات GitHub المنفذة مع حالتها
21. Admin يفحص الكود الحالي ويحدد الملفات المطلوبة لتنفيذ GitHub Integration Panel
