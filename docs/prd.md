# مستند المتطلبات

## 1. نظرة عامة على التطبيق

### 1.1 اسم التطبيق
نظام ربط المتجر مع Reseller API وإدارة طلبات شحن المحفظة - المرحلة الأولى

### 1.2 وصف التطبيق
نظام خلفي آمن يجمع بين:
- ربط المتجر مع Reseller API باستخدام بيئة Sandbox
- إدارة طلبات شحن محفظة Vodafone Cash مع نظام مطابقة تلقائية محسّن يعتمد على القيمة المصغرة الفريدة
- واجهة للعملاء لإنشاء طلبات الشحن
- واجهة للأدمن لإدارة الطلبات والموافقة عليها
- تطبيق Android لاستقبال رسائل SMS وإرسالها تلقائياً

## 2. المستخدمون وسيناريوهات الاستخدام

### 2.1 المستخدمون المستهدفون
- العميل (Customer): يطلب شحن محفظته بالكريدت
- مدير النظام (Admin): يدير الاتصال مع Provider ويوافق على طلبات الشحن
- تطبيق Android: يستقبل رسائل Vodafone Cash ويرسلها للنظام

### 2.2 سيناريوهات الاستخدام الأساسية
- العميل يطلب شحن محفظته بعدد معين من الكريدت
- العميل يحوّل المبلغ المحسوب (بالقروش الفريدة) إلى رقم فودافون كاش الرسمي
- تطبيق Android يستقبل رسالة Vodafone Cash ويرسل بياناتها للنظام
- النظام يطابق الرسالة تلقائياً مع الطلب باستخدام رقم المرسل والمبلغ الدقيق
- الأدمن يوافق يدوياً على الطلبات التي فشلت المطابقة التلقائية
- الأدمن يختبر الاتصال مع Provider ويزامن الخدمات والرصيد

### 3.1 صفحة طلب الشحن (Customer)

#### 3.1.1 عرض رقم فودافون كاش الرسمي
- عرض الرقم: 01097273680
- زر نسخ الرقم

#### 3.1.2 خانة عدد الكريدت
- المستخدم يدخل عدد الكريدت المطلوب
- التحقق من أن القيمة رقم صحيح أكبر من صفر

#### 3.1.3 خانة السعر الإجمالي
- محسوب تلقائياً: عدد الكريدت × 300 جنيه + قيمة مصغرة فريدة
- القيمة المصغرة (Fingerprint Amount): قروش عشوائية بين 0.01 و 0.99
- مثال: 2 كريدت = 600.22 جنيه
- عرض المبلغ بالقروش الكاملة
- زر نسخ المبلغ الإجمالي

#### 3.1.4 خانة رقم فودافون كاش المحوِّل
- المستخدم يدخل رقم محفظته
- التحقق من صحة الرقم (11 رقم يبدأ بـ010 أو 011 أو 012 أو 015)

#### 3.1.5 خانة اسم صاحب المحفظة
- اختياري لكن موصى به
- يساعد في المطابقة اليدوية

#### 3.1.6 ملاحظة للمستخدم
- عرض تنبيه: يجب تحويل المبلغ بالقيمة الكاملة بما في القروش

#### 3.1.7 زر إرسال الطلب
- حفظ الطلب في قاعدة البيانات بحالة معلقة
- توليد القيمة المصغرة الفريدة وحفظها

### 3.2 صفحة إدارة طلبات الشحن (Admin)

#### 3.2.1 قائمة الطلبات
- عرض جميع الطلبات مع:
  - رقم الطلب
  - رقم المحوِّل
  - اسم المحوِّل (إن وُجد)
  - عدد الكريدت
  - المبلغ الإجمالي (بالقروش الفريدة)
  - القيمة المصغرة (Fingerprint)
  - الحالة: معلقة / موافق عليها / مرفوضة
  - تاريخ الإنشاء
  - تفاصيل الرسالة المستلمة (إن وُجدت):
    - رقم المرسل من SMS
    - اسم المرسل من SMS
    - المبلغ من SMS
    - كود المعاملة

#### 3.2.2 الفلترة
- فلترة حسب الحالة: الكل / معلقة / موافق عليها / مرفوضة

#### 3.2.3 الموافقة اليدوية
- زر الموافقة لكل طلب معلق
- زر الرفض لكل طلب معلق
- عرض سبب فشل المطابقة التلقائية (إن وُجد)

### 3.3 صفحة الإعدادات (Admin)

#### 3.3.1 رقم فودافون كاش الرسمي

### 3.5 Provider Connection Service

#### 3.5.1 المصادقة
- إرسال طلبات HTTP مع Authorization: Bearer ${PROVIDER_API_KEY}
- التحقق من صحة المصادقة

#### 3.5.2 جلب الخدمات
- استدعاء GET /api/v1/services من Reseller API
- معالجة Response Envelope: {success, data, meta}
- حفظ request_id في السجلات

#### 3.5.3 جلب الرصيد
- استدعاء GET /balance من Reseller API
- معالجة البيانات المستلمة
- حفظ request_id في السجلات

#### 3.5.4 معالجة الأخطاء
- التعامل مع HTTP status codes
- معالجة timeout
- معالجة rate-limit
- تسجيل الأخطاء دون كشف معلومات سرية

### 3.6 Provider Health Check

### 3.10 Wallet Topup Service

#### 3.10.1 إنشاء طلب شحن
- استقبال بيانات الطلب من العميل
- توليد القيمة المصغرة الفريدة (0.01 - 0.99)
- حساب المبلغ الإجمالي: عدد الكريدت × 300 + القيمة المصغرة
- حفظ الطلب في جدول wallet_topup_requests بحالة pending

#### 3.10.2 الموافقة على الطلب
- تحديث حالة الطلب إلى approved
- إضافة الكريدت إلى رصيد العميل

#### 3.10.3 رفض الطلب
- تحديث حالة الطلب إلى rejected

### 3.11 SMS Webhook Handler

#### 3.11.1 استقبال البيانات
- استقبال webhook من تطبيق Android
- البيانات المستلمة:
  - sender_phone: رقم المحوِّل
  - sender_name: اسم المحوِّل (إن وُجد)
  - amount: المبلغ المحوَّل (بالقروش الكاملة)
  - transaction_id: كود المعاملة
  - sms_body: نص الرسالة الكامل

#### 3.11.2 تحليل محتوى الرسالة
- استخراج البيانات من نص الرسالة إذا لم تكن محللة مسبقاً
- دعم الرسائل العربية والإنجليزية
- الأنماط المدعومة:
  - عزيزي العميل، لقد استلمت من [الاسم / رقم_المحفظة] مبلغ [X] جنيه في [التاريخ والوقت] ورصيدك الحالي [Y] جنيه. كود المعاملة: [CODE]
  - You have received EGP [X] from [Name/Number] on [Date]. Transaction ID: [CODE]. Balance: [Y] EGP.

#### 3.11.3 حفظ البيانات
- حفظ بيانات الرسالة في جدول sms_logs

#### 3.11.4 تشغيل المطابقة التلقائية
- استدعاء Auto-Match Engine

### 3.12 Auto-Match Engine

#### 3.12.1 منطق المطابقة المحسّن
- البحث عن طلبات معلقة (pending) تطابق:
  - sender_phone = رقم المحوِّل من SMS
  - |fingerprint_amount - amount من SMS| ≤ 0.01

#### 3.12.2 المطابقة الناجحة
- تحديث حالة الطلب إلى approved
- ربط الطلب بـtransaction_id
- حفظ sender_name من SMS
- إضافة الكريدت إلى رصيد العميل

#### 3.12.3 فشل المطابقة
- الطلب يبقى بحالة pending
- حفظ سبب الفشل في سجل الطلب
- الأدمن يوافق يدوياً

## 4. القواعد والمنطق

### 4.1 الأمان

#### 4.1.1 حماية API Key
- API Key يجب أن يكون Server-side Secret/Environment Variable فقط
- عدم حفظ المفتاح في Database أو Source Code أو Logs
- عدم عرض API Key في Dashboard أو API responses
- عدم السماح للعميل بإرسال أو تعديل provider credentials

#### 4.1.2 معمارية الطلبات
- جميع طلبات Reseller API تمر من Backend
- Frontend لا يتصل مباشرة بـReseller API
- عدم الثقة بأي سعر أو service code أو balance value قادم من Frontend

#### 4.1.3 المصادقة والتفويض
- إضافة authentication وauthorization للـBackend endpoints
- إضافة basic rate limiting على endpoints الحساسة

#### 4.1.4 الاتصالات
- استخدام HTTPS للاتصالات
- منع تسريب secrets في error messages وlogs

### 4.2 إعدادات البيئة

#### 4.2.1 متغيرات البيئة
- PROVIDER_API_BASE_URL: https://api.geminioffer.web.id/api/v1
- PROVIDER_API_KEY: مفتاح Sandbox
- PROVIDER_ENVIRONMENT: sandbox

#### 4.2.2 الاستخدام
- استخدام Sandbox فقط في هذه المرحلة
- النظام مجهز للانتقال إلى Live بتغيير Environment Variables فقط

### 4.3 Provider API

#### 4.3.1 المصادقة
- Authorization: Bearer ${PROVIDER_API_KEY}

#### 4.3.2 Response Envelope
- الهيكل: {success, data أو error, meta}
- فحص success وerror.code وdata

#### 4.3.3 Request ID
- حفظ request_id في logs لتسهيل debugging

### 4.4 معالجة الأخطاء

#### 4.4.1 HTTP Status Codes
- 200: نجاح
- 400: طلب غير صحيح
- 401: مصادقة فاشلة
- 403: غير مصرح
- 404: غير موجود
- 429: تجاوز الحد - قراءة Retry-After
- 500: خطأ في الخادم
- 503: الخدمة غير متاحة

#### 4.4.2 عرض الأخطاء
- عرض رسائل خطأ واضحة
- عدم كشف secrets في رسائل الخطأ

### 4.6 نظام القيمة المصغرة (Fingerprint Amount)

#### 4.6.1 التوليد
- توليد قيمة عشوائية بين 0.01 و 0.99 لكل طلب
- القيمة فريدة لكل طلب حتى لو نفس المستخدم

#### 4.6.2 الاستخدام
- إضافة القيمة إلى المبلغ الأساسي (عدد الكريدت × 300)
- مثال: 2 كريدت = 600 + 0.22 = 600.22 جنيه

#### 4.6.3 المطابقة
- مطابقة المبلغ من SMS مع fingerprint_amount بدقة ≤ 0.01
- هذا يحل مشكلة التعرف عند غياب اسم صاحب المحفظة

### 4.7 نظام المطابقة التلقائية المحسّن

#### 4.7.1 معايير المطابقة
- رقم المرسل من SMS = sender_phone في الطلب
- |المبلغ من SMS - fingerprint_amount| ≤ 0.01

#### 4.7.2 أولوية المطابقة
- إذا تطابق أكثر من طلب: اختيار الأقدم

#### 4.7.3 حالات فشل المطابقة
- لا يوجد طلب معلق بنفس رقم المرسل
- المبلغ لا يطابق أي fingerprint_amount
- الطلب المطابق تمت الموافقة عليه مسبقاً

- إنجليزي: You have received EGP [X] from [Name/Number] on [Date]. Transaction ID: [CODE]. Balance: [Y] EGP.

#### 4.8.2 البيانات المستخرجة
- sender_phone: رقم المحوِّل
- sender_name: اسم المحوِّل (إن وُجد)
- amount: المبلغ المحوَّل (بالقروش الكاملة)

## 5. الحالات الاستثنائية والحدودية

| الحالة | السلوك المتوقع |
|--------|----------------|
| فشل الاتصال بـProvider | عرض رسالة خطأ واضحة، تسجيل الخطأ في Logs، عدم كشف API Key |
| مصادقة فاشلة (401) | عرض \"Authentication Invalid\"، تسجيل الخطأ، التحقق من صحة API Key في Environment Variables |
| تجاوز الحد (429) | قراءة Retry-After، الانتظار قبل إعادة المحاولة، تسجيل الحدث |
| خطأ في الخادم (500/503) | عرض رسالة خطأ عامة، تسجيل request_id، عدم كشف تفاصيل داخلية |
| timeout | إعادة المحاولة مرة واحدة، تسجيل الخطأ إذا فشلت المحاولة الثانية |
| خدمة غير موجودة في Provider | عدم حذف الخدمة من Database، تحديث status إلى unavailable |
| Frontend يحاول الوصول مباشرة لـProvider API | رفض الطلب، عدم السماح بأي اتصال مباشر |
| محاولة عرض API Key في Dashboard | عدم عرض المفتاح تحت أي ظرف |
| العميل يدخل عدد كريدت غير صحيح | عرض رسالة خطأ: يجب إدخال رقم صحيح أكبر من صفر |
| العميل يدخل رقم محفظة غير صحيح | عرض رسالة خطأ: يجب إدخال رقم فودافون كاش صحيح (11 رقم) |
| استلام رسالة SMS لا تطابق أي طلب | حفظ الرسالة في sms_logs دون مطابقة، الأدمن يراجع يدوياً |
| استلام رسالة SMS تطابق طلب تمت الموافقة عليه | تجاهل الرسالة، تسجيل الحدث |
| المبلغ المحوَّل أقل من المطلوب | فشل المطابقة التلقائية، الأدمن يراجع يدوياً |

## 6. معايير القبول

1. العميل يفتح صفحة طلب الشحن ويرى رقم فودافون كاش الرسمي 01097273680 مع زر نسخ
2. العميل يدخل 2 كريدت ويرى السعر الإجمالي محسوباً تلقائياً (مثلاً 600.22 جنيه) مع زر نسخ المبلغ
3. العميل يدخل رقم محفظته واسمه (اختياري) ويضغط إرسال الطلب، ويُحفظ الطلب بحالة معلقة
4. العميل يحوّل المبلغ 600.22 جنيه إلى رقم فودافون كاش الرسمي
5. تطبيق Android يستقبل رسالة Vodafone Cash ويستخرج: رقم المرسل + اسمه + المبلغ 600.22 + كود المعاملة، ويرسل webhook للنظام
6. النظام يطابق الرسالة تلقائياً مع الطلب (رقم المرسل + المبلغ الدقيق) ويوافق على الطلب ويضيف 2 كريدت لرصيد العميل
7. الأدمن يفتح صفحة إدارة الطلبات ويرى الطلب بحالة موافق عليها مع تفاصيل الرسالة المستلمة
8. الأدمن يفلتر الطلبات حسب الحالة (معلقة / موافق عليها / مرفوضة) ويرى النتائج الصحيحة
9. الأدمن يفتح صفحة الإعدادات ويرى إحصائيات الشحن: إجمالي الطلبات / الموافق عليها تلقائياً / يدوياً / المرفوضة
10. الأدمن يغيّر رقم فودافون كاش الرسمي في الإعدادات ويرى الرقم الجديد في صفحة طلب الشحن
11. Admin يفتح Provider Panel ويرى البيئة معروضة كـSANDBOX
12. Admin يضغط على Test Connection ويرى نتائج الاختبار: Authentication PASS، GET /services PASS، GET /balance PASS
13. Admin يضغط على Sync Services وتظهر الخدمات المحدثة في قاعدة البيانات مع جميع الحقول المطلوبة
14. Admin يضغط على Refresh Balance ويرى الرصيد الحالي محدثًا مع آخر وقت مزامنة
15. المطور يتحقق من أن API Key محفوظ في Environment Variables فقط وغير موجود في Database أو Source Code
