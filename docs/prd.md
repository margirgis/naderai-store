# مستند المتطلبات

## 1. نظرة عامة على التطبيق

### 1.1 اسم التطبيق
نظام Nader AI SMS Reader - نظام متكامل لإدارة طلبات شحن المحفظة مع تطبيق Android ذكي

### 1.2 وصف التطبيق
نظام متكامل يجمع بين:
- تطبيق Android (Nader AI SMS Reader) يتصل بالنظام الخلفي ويسجل بيانات الجهاز
- نظام خلفي يدير الأجهزة المتصلة ويوزع مهام فحص الرسائل
- واجهة للعملاء لإنشاء طلبات شحن المحفظة
- واجهة للأدمن لإدارة الأجهزة والطلبات
- آلية تلقائية لفحص رسائل SMS والتحقق من المعاملات
- نظام موافقة تلقائية وإضافة الكريدت
- تكامل مع Reseller API (بيئة Sandbox)
- تكامل مع GitHub لإدارة الملفات

## 2. المستخدمون وسيناريوهات الاستخدام

### 2.1 المستخدمون المستهدفون
- العميل: يطلب شحن محفظته بالكريدت
- مدير النظام: يدير الأجهزة المتصلة والطلبات والموافقات
- تطبيق Android: يتصل بالنظام ويفحص رسائل SMS

### 2.2 سيناريوهات الاستخدام الأساسية
- تطبيق Android يتصل بالنظام ويسجل بيانات الجهاز
- العميل يطلب شحن محفظته ويحوّل المبلغ
- النظام يوزع مهمة الفحص على جهاز متصل
- التطبيق يفحص جميع رسائل SMS ويبحث عن رسالة المعاملة
- التطبيق يرسل نتيجة الفحص للنظام
- النظام يوافق تلقائياً ويضيف الكريدت عند النجاح
- الأدمن يراقب الأجهزة والطلبات

### 3.5 صفحة طلب الشحن (Customer)

#### 3.5.1 عرض رقم فودافون كاش الرسمي

#### 3.5.2 خانة عدد الكريدت
- المستخدم يدخل عدد الكريدت المطلوب

#### 3.5.4 خانة رقم فودافون كاش المحوِّل

#### 3.5.5 خانة اسم صاحب المحفظة
- اختياري

#### 3.5.6 ملاحظة للمستخدم
- عرض تنبيه: يجب تحويل المبلغ بالقيمة الكاملة بما في القروش

#### 3.5.7 زر إرسال الطلب

#### 3.13.2 التحقق من النتيجة

#### 3.13.3 حفظ النتيجة
- تحديث حالة المهمة: completed / failed
- حفظ بيانات الرسالة في جدول sms_logs_devices
- تحديث حالة الطلب: verified / pending

### 3.14 Auto Approval Service

#### 3.14.1 التحقق من نجاح الفحص
- عند استقبال نتيجة فحص ناجحة
- التحقق من مطابقة البيانات:
  - المبلغ من الرسالة = المبلغ المطلوب (بدقة ≤ 0.01)
  - رقم المحوِّل من الرسالة = رقم المحوِّل في الطلب

#### 3.14.2 الموافقة التلقائية
- تحديث حالة الطلب: approved
- إضافة الكريدت إلى رصيد العميل
- حفظ transaction_id
- حفظ sender_name

#### 3.14.3 فشل التحقق
- تحديث حالة الطلب: pending
- حفظ سبب الفشل
- الأدمن يوافق يدوياً

## 4. القواعد والمنطق

### 4.1 الأمان

#### 4.1.1 حماية API Keys
- PROVIDER_API_KEY و GITHUB_TOKEN يجب أن يكونا Environment Variables فقط
- عدم حفظ المفاتيح في Database أو Source Code أو Logs
- عدم عرض المفاتيح في Dashboard أو API responses

#### 4.1.2 أذونات التطبيق Android
- READ_SMS: لقراءة رسائل SMS
- INTERNET: للاتصال بالنظام
- FOREGROUND_SERVICE: لتشغيل الخدمة في الخلفية
- POST_NOTIFICATIONS: لعرض الإشعارات

#### 4.1.3 المصادقة والتفويض
- إضافة authentication للـBackend endpoints
- التحقق من Device ID عند استقبال البيانات من التطبيق

### 4.2 إعدادات البيئة

#### 4.2.1 متغيرات البيئة
- PROVIDER_API_BASE_URL: https://api.geminioffer.web.id/api/v1
- PROVIDER_API_KEY: مفتاح Sandbox
- PROVIDER_ENVIRONMENT: sandbox
- GITHUB_TOKEN: Token المصادقة مع GitHub
- GITHUB_REPO_OWNER: اسم مالك المستودع
- GITHUB_REPO_NAME: اسم المستودع
- BACKEND_URL: عنوان النظام الخلفي

### 4.4 Endpoints الجديدة

#### 4.4.1 Device Registration
- POST /api/device/register
- Body: device_id, device_model, android_version, app_version, phone_number
- Response: success, device_id

#### 4.4.2 Device Heartbeat
- POST /api/device/heartbeat
- Body: device_id
- Response: success, pending_tasks

#### 4.4.3 Task Result
- POST /api/device/task-result
- Body: task_id, status, result_data, failure_reason
- Response: success

#### 4.4.4 Get Device Tasks
- GET /api/device/tasks?device_id={device_id}
- Response: tasks[]

#### 4.4.5 Admin - Get Devices
- GET /api/admin/devices
- Response: devices[]

#### 4.4.6 Admin - Get Device Details
- GET /api/admin/devices/{device_id}
- Response: device, tasks[]

### 4.6 منطق فحص SMS

#### 4.6.1 فلترة الرسائل
- قراءة رسائل SMS من آخر 7 أيام
- فلترة رسائل Vodafone Cash فقط

#### 4.6.2 المطابقة
- مطابقة المبلغ: |amount من SMS - fingerprint_amount| ≤ 0.01
- مطابقة رقم المحوِّل: sender_phone من SMS = sender_phone في الطلب

#### 4.6.3 النتيجة
- نجاح: إرسال بيانات الرسالة الكاملة
- فشل: إرسال سبب الفشل (لم يتم العثور على رسالة مطابقة)

#### 4.7.2 الإجراءات

## 5. الحالات الاستثنائية والحدودية

| الحالة | السلوك المتوقع |
|--------|----------------|
| الجهاز غير متصل عند إنشاء طلب | الانتظار حتى اتصال جهاز، أو عرض رسالة للعميل |
| فشل فحص SMS | إعادة توزيع المهمة على جهاز آخر |
| عدم وجود رسالة مطابقة | حفظ سبب الفشل، الأدمن يوافق يدوياً |
| الجهاز يفقد الاتصال أثناء الفحص | إعادة توزيع المهمة بعد 5 دقائق |
| استقبال نتيجة فحص لمهمة منتهية | تجاهل النتيجة |
| التطبيق لا يملك إذن READ_SMS | عرض رسالة طلب الإذن |
| فشل إرسال النتيجة للنظام | إعادة المحاولة 3 مرات |
| جهاز واحد يستقبل مهام متعددة | معالجة المهام بالتسلسل |
| المبلغ المحوَّل لا يطابق المطلوب | فشل الفحص، الأدمن يوافق يدوياً |
| رقم المحوِّل لا يطابق | فشل الفحص، الأدمن يوافق يدوياً |

## 6. معايير القبول

1. تطبيق Android يبدأ ويسجل بيانات الجهاز في النظام
2. الأدمن يفتح صفحة الأجهزة المتصلة ويرى الجهاز بحالة online
3. العميل يفتح صفحة طلب الشحن ويدخل 2 كريدت ورقم محفظته ويضغط إرسال
4. النظام يحفظ الطلب بحالة pending ويوزع مهمة الفحص على الجهاز المتصل
5. التطبيق يستقبل المهمة ويعرض إشعار
6. التطبيق يفحص جميع رسائل SMS ويبحث عن رسالة تطابق المبلغ ورقم المحوِّل
7. التطبيق يرسل نتيجة الفحص للنظام (نجاح + بيانات الرسالة)
8. النظام يوافق تلقائياً على الطلب ويضيف الكريدت للعميل
9. الأدمن يفتح صفحة إدارة الطلبات ويرى الطلب بحالة approved
10. الأدمن يفتح تفاصيل الطلب ويرى بيانات الرسالة المطابقة
11. التطبيق يعرض الطلب في قائمة آخر الطلبات المفحوصة
12. الجهاز يفقد الاتصال، النظام يحدث حالته إلى offline بعد دقيقتين
13. الجهاز يستعيد الاتصال، النظام يحدث حالته إلى online
